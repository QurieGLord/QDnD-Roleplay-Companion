# Повышение — механики, сквозные связи и проверка готовности

9 октября 2026. Требование автора: учитывать весь путь развития, отделять навыки/владения от способностей, сохранять свободу стола и улучшать UI/UX. Успех отдельных проверок не закрывает всю механику повышения. Текущий рабочий код ещё не установлен в основной пакет.

## Политика состояния — принята

Повышение не лечит: 18/30 → 18/36. Изменение Телосложения увеличивает максимум с учётом прежних уровней; текущие ОЗ остаются прежними. Ячейки/заряды получают только положительный прирост нормы, 1/3 → 2/4, 6/4 → 7/5. Новый действительно приобретаемый ресурс получает начальный запас. Ручные значения, превышения, состояние, форма, временные ОЗ, концентрация, заметки и инвентарь не стираются. Обычные нормативные ограничения и домашние исключения различаются; поддержка исключений не требует редактора кода.

## Узкие места, которые нельзя спрятать интерфейсом

1. Суммарный hitDice и общий spellSlots не описывают все смешанные ресурсы. Без раздельного хранения и миграции красивый выбор класса будет давать неверный результат. Текущий пользовательский мастер поэтому честно сообщает, что сочетание классов ещё не поддерживается, без изменения героя; калькуляторы и черновик уже проверяются отдельно.
2. Плоский список knownSpells не хранит происхождение и специальные способы применения. Нужны устойчивые связи, а не догадки по имени. Старые записи и ID сохраняются при добавлении данных.
3. Булево «использовано» не выражает дополнительные применения, разрешённые мастером. Необходимо согласованное представление норм/остатков для таких возможностей, без потери старых значений.
4. Несколько каталогов и слои импортов могут смешивать одинаковые названия/ID или две редакции. Это нельзя лечить подстрочным выбором первого варианта. Нужны происхождение, профиль и диагностика незавершённого выбора.
5. Добавление формы в UI не считается реализацией правила. Выдача, применение, расход, восстановление и перенос проверяются как один путь.
